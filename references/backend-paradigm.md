# 后端工作范式

> 适用：云函数、微服务、单体 API 等一切服务端层。

## 1. 函数即服务边界

- 每个服务单元只做一件事，按业务域划分（user / goods / order / pay / shipment / aftersale / admin ...）。
- 同类 CRUD 可合并为一个函数按 `action` 分发（如 `cartCRUD`），减少部署单元数量。
- 共享逻辑下沉 `common/`：鉴权、单号生成、金额校验、DB 封装、常量与错误码、第三方 SDK 封装。**common 只允许纯函数与数据访问，不允许藏业务状态。**

## 2. 写操作五步法（任何写入口必须全走）

```
鉴权 → 参数校验 → 幂等检查 → 事务写入 → 留痕（操作日志/流水）
```

缺一步即视为未完成。读操作至少走：鉴权 → 参数校验。

## 3. 幂等设计

- 所有提交类接口支持幂等键（客户端重试带同一 key，服务端命中返回原结果）。
- 回调类入口（支付回调、消息推送）必须：验签 → 解密 → 幂等（按回调唯一标识去重）→ 应答规范（验签失败回 4xx 让对方重推，不静默吞）。
- 单号全局唯一：服务端生成，规则统一（前缀 + 时间戳 + 序列），客户端禁止传单号。
- 条件更新防超卖：`UPDATE ... WHERE stock >= N` 并检查影响行数，不用"读出-判断-写回"。

## 4. 统一响应与错误码

```json
{ "code": 0, "msg": "ok", "data": { } }
```

| code | 含义 |
| --- | --- |
| 0 | 成功 |
| 1001 | 参数错误 |
| 1002 | 未登录 / token 失效 |
| 1003 | 无权限 |
| 2001 | 业务校验失败（msg 带具体原因） |
| 2002 | 重复提交（幂等拦截） |
| 3001 | 第三方（支付/推送等）异常 |
| 5000 | 系统异常 |

错误码语义全局唯一，不随业务域重复定义同码不同义。新增错误码必须登记进契约文档通用约定章。

## 5. 数据红线

- **金额一律整数「分」**，禁止浮点；字段名带 `Amount/Fee/Price` 后缀。
- **时间一律 ISO 8601 UTC 字符串**；凡是按"本地墙钟"判定的逻辑（打卡、预约时段、过期、定时任务）**显式锁定时区**（如 Node `process.env.TZ='Asia/Shanghai'`，用 `=` 赋值不用 `||`——平台可能显式设成 UTC）。部署后第一件事验证运行时实际时区。
- **快照机制**：订单生成时冗余商品名/规格/单价/图片快照，商品后续改价/改名/下架不影响历史订单。
- 软删除：`deleted: true` + `deletedAt`；流水类集合不删除只追加。

## 6. 配置与密钥

- 密钥只放服务端环境变量与本地 `.env`（gitignore），**禁止写进文档/聊天记录/代码**。
- 多环境（dev/prod）配置分别存档；部署到环境 E 前必须核对并复制 E 的配置文件，部署后逐函数复读环境变量（防配置漂移事故）。
- 部署包剪枝：剔除开发依赖（如原生编译的二进制），部署后打 `buildInfo` 版本探针用于复读确认。

## 7. 定时任务

- 统一调度器入口：定时事件带触发器名，命中即单跑该任务；未命中回落为时刻分流 tick。
- 任务必须幂等可重跑（补跑历史积压是预期行为）。
- 任务执行落 `job_logs`（任务名、时刻、结果），可审计。

## 8. 消息推送接收端（回调类入口实例）

支付回调、订阅消息推送、第三方事件通知共用同一套样板：

```
验签 → 解密 → 幂等落库 → 业务处理 → 规范应答
```

任何一步失败都必须给出明确应答，**禁止静默吞消息**（§3 回调入口要求的展开）。

### 8.1 验签

- 用推送方分配的 token 计算签名（常见为 `HMAC-SHA256(排序后参数 + timestamp + nonce + body, token)`），与推送方 `signature` 字段比对；**比较用恒定时间函数**，防时序侧信道。
- 时间戳容差 ±5 分钟，超出视为重放攻击直接拒绝。
- 验签不过：回 4xx 或约定错误码让推送方重推；**不要 return 200 后丢弃**——静默成功会让对端永远不重推、问题永远暴露不了。

### 8.2 AES 解密

- 算法与密钥来源以推送方文档为准（常见 AES-256-CBC），密钥与 IV 放服务端环境变量（§6 密钥红线），禁止写进代码、文档、聊天记录。
- 流程：Base64 解码 → 解密 → PKCS7 去 padding → `JSON.parse`；每步失败分别记日志并归错误码 3001，便于区分"对端配错"与"自身实现错"。
- 解密成功后，**原文与解密文一起先落 `push_inbox` 留痕**（接收时间、来源 IP、原始报文、解密报文），再进业务处理。

### 8.3 幂等落库

- 回调唯一标识（`msgId` / `eventId`）在 `push_inbox` 上建**唯一索引**：插入成功 = 首次消费；唯一索引冲突 = 重复推送，直接返回与首次相同的应答。
- 落库与应答解耦：应答前必须完成 inbox 落库（同步），业务处理可异步；inbox 记录状态机 `pending → success / failed` + 重试次数，推送方重推时按 inbox 状态应答，不重复执行业务。
- 业务侧再叠加自身幂等键（§3），双保险——inbox 挡推送方重推，业务幂等键挡自己内部重试。

### 8.4 应答规范

| 场景 | 应答 |
| --- | --- |
| 验签失败 | 4xx 或约定错误码，让推送方重推 |
| 解密失败 | 按约定错误码应答并告警（多半是对端配置错，重推无用也要应答） |
| 首次消费 | 约定成功格式（如 `{"code": 0}`），且 inbox 已落库 |
| 重复推送 | 返回首次处理结果，不重复落库、不重复触发业务 |

### 8.5 易错清单（真实事故复盘）

- **只验签不幂等** → 推送方重推导致积分/库存/到账重复入账；对账时才发现差额。
- **先回 200 再慢慢处理** → 进程被杀消息永久丢失；应答前必须落 inbox，业务可异步。
- **时区坑** → 回调时间戳按 UTC 解析，与本地墙钟比对误判"过期"丢消息（§5 时区锁）。
- **密钥进代码/日志** → 红线（§6），轮换密钥时按环境逐台复读。
- **应答格式随实现漂移** → 成功格式以契约文档为准，改格式 = 契约变更，走硬规则。

## 9. 验收要点

- [ ] 每个写入口五步法齐全
- [ ] 全量错误码与契约一致
- [ ] 回调入口验签 + 幂等 + 应答规范
- [ ] 金额无浮点、时间带时区锁
- [ ] 关键链路（支付/库存/状态扭转）有单测且 PR 附证据
- [ ] 部署后版本探针复读通过
