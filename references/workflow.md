## 阶段① 需求梳理

**目标**：把用户的口述需求变成一份可施工的 PRD，并由用户拍板范围。

步骤：

1. 用 `assets/templates/prd-template.md` 建 `docs/prd.md`。必填章节：项目概述、用户角色、技术架构、信息架构、C 端功能需求（按页列出）、后台功能需求、接口核心清单、数据库集合清单、核心业务流程、非功能需求、第三方接入、迭代规划（🅿️0/🅿️1/🅿️2 标注）、关键验收标准、风险与待确认事项。
2. 需求中所有"以后再说"的功能，显式标 🅿️1/🅿️2，不混入 🅿️0。
3. 每页功能写清：入口、操作、数据从哪个接口来、提交到哪个接口、异常态（空/加载/失败/无权限）。
4. 把 PRD 交给用户确认，**用户确认前不进入阶段②**。确认意见当日落回文档。

常见坑：

- 需求只写"happy path"，异常态和边界（空列表、网络失败、未登录、库存不足）全部漏掉 → 前端后期返工。
- 验收标准模糊（"好用""流畅"）→ 必须量化（如"列表页首屏加载 < 2s""验收集 30 分钟全过"）。

## 阶段② 美术风格确认

**目标**：在进入任何编码之前，先让用户看到并确认最终产品的样子。

步骤：

1. 由设计 agent 产出《美术风格指导》（模板 `art-style-guide-template.md`）：风格定位、色彩体系（主色/辅色/功能色 + 色值）、字体规范、间距栅格、组件规范（按钮/卡片/表单）、**美术禁忌清单**、视觉验收清单。
2. 用**纯 HTML + CSS**（可用 Tailwind CDN）实现关键页面的高保真静态预览，不接入任何真实数据（用占位图/假数据）。多页面时逐页出预览。
3. 用户以"业主裁决"方式逐条确认或打回；打回项写入《美术风格审查整改报告》，按严重度分级（P1 必须改 / P2 应当改 / 通过项），整改后复核。
4. 产出《品牌与文案规范》：品牌名、主张、程序介绍文案、语气规范。所有界面文案从这里取，禁止现场编造。

常见坑：

- 跳过 HTML 预览直接写业务代码 → 用户看到成品才提风格意见，全部重写。
- 风格指导不写禁忌清单 → AI 生成的界面默认"渐变+阴影+圆角全家桶"，风格失控。禁忌必须显式列（如"禁止大面积渐变""禁止圆角超过 8px"）。

## 阶段③ 前端构建

**目标**：前端 agent 按确认过的 UI 稿实现全部页面，并把接口需求固化成契约。

步骤：

1. 前端 agent 只读三样：PRD、美术风格指导、UI 预览 HTML。
2. 实现页面时遵守前端范式（见 `references/frontend-paradigm.md`）：主题即配置、金额只展示不算账、所有接口走统一 request 封装。
3. **每实现一个页面，同步在接口契约文档中登记它消费的接口**：接口名、入参、出参字段（逐字段：名/类型/必填/含义/示例）、错误码。前端对出参字段的描述是契约的"需求侧事实"。
4. 页面完成后，前端 agent 输出《前端 UI 细节审核报告》自检：逐页核对字号/按钮/间距/位置是否符合风格指导。
5. master 汇总前端契约草稿，与后端、数据库的契约草稿**合并去重、消除冲突**，冻结为唯一契约文档。

常见坑：

- 前端自行 mock 一套字段名，联调时与后端出参对不上 → 契约必须在编码前冻结，不是联调时对出来。
- 前端做金额计算（单价 × 数量求和）→ 金额一律服务端为准，前端只渲染。

## 阶段④ 后端搭建

**目标**：后端 agent 按契约实现服务，并对契约的"供给侧事实"负责。

步骤：

1. 后端 agent 只读：PRD、冻结的接口契约、后端需求文档。
2. 按后端范式（`references/backend-paradigm.md`）施工：函数即边界、写操作五步法（鉴权→校验→幂等→事务→留痕）、统一响应格式、统一错误码。
3. 每个接口实现后，**回读契约文档原文逐字段核对**——禁止凭记忆；不一致处提出契约修订（走硬规则），不擅自改字段。
4. 关键链路（支付回调、库存扣减、状态扭转）必须写单元测试，PR 附测试证据（日志/用例编号）。
5. 定时任务类功能，本地开发时用"手动触发入口"验证，上线前再配调度器；同时检查运行时默认时区并显式锁定（`process.env.TZ='Asia/Shanghai'` 或等价手段，**用 `=` 不用 `||`**）。

常见坑：

- 幂等只做在客户端防重复点击 → 服务端必须幂等（唯一约束/幂等键/条件更新），回调类入口（支付/推送）尤其要验签 + 幂等。
- 时间字段存本地时间 → 统一 ISO 8601 UTC 字符串，展示层再转本地；判定类逻辑（打卡、过期、时段）显式锁时区。
- 部署配置漂移：向环境 E 部署前必须核对目标环境的密钥/回调域名配置，部署后逐函数复读环境变量。

## 阶段⑤ 数据库搭建

**目标**：数据库 agent 产出权威 DDL，集合/表与枚举状态机全部登记。

步骤：

1. 数据库 agent 只读：PRD、后端需求文档、契约文档。
2. 按数据库范式（`references/database-paradigm.md`）出：集合关系总览图、逐集合详细设计（字段/类型/索引/默认值）、索引汇总清单、**枚举与状态机汇总（唯一权威定义）**、数据生命周期与归档规则。
3. DDL 变更只走 `scripts/migrations/` 迁移脚本，幂等（`IF NOT EXISTS` / 动态补列），禁止手改生产库。
4. 与后端确认：本地开发库可用 SQLite 驱动跑迁移脚本，生产用正式 DDL，两边字段口径一致。
5. 契约中出现的任何枚举值（订单状态、错误码语义等），必须能在数据库文档第 6 章找到权威定义，找不到就补登。

常见坑：

- 枚举魔法值散落各处（"pending"/0/"PENDING" 混用）→ 强制字符串枚举，唯一登记处。
- 需求与 CHECK 约束冲突（如"允许记负" vs `CHECK balance>=0`）→ 显式记录口径偏差声明，用负债字段承接，不静默违反约束。

## 阶段⑥ 测试验收

**目标**：独立测试 agent 不按实现、只按文档执行验收。

步骤：

1. 测试 agent **不读业务实现代码**（防被实现带偏），只读 PRD、契约、测试用例文档。
2. 用 `test-cases-template.md` 维护用例：核心链路集、特色机制集、后台集；每轮新增功能补"用例集 N"并全量回归。
3. 自动化用脚本跑（`scripts/probe_api.py` 打底 + 项目专属测试脚本），结果记录"N/N 绿"。
4. 出具测试报告：通过清单、失败清单（含复现步骤、日志）、遗留风险。失败项不过，不进入阶段⑦。
5. 验收集：用户亲自按用例走 30 分钟，签字确认。

常见坑：

- 时间依赖性用例硬编码"今天 11:00-12:00"→ 中午后必挂；用动态窗口（当前+2h，深夜顺延明天）。
- 测试 agent 看了实现后把"实现如此"当"应当如此"→ 保持独立，以文档为准。

## 阶段⑦ MVP 与⑧迭代

- MVP 门槛：核心链路（通常是"下单→支付→履约"）全绿 + 用户验收集全过 + 部署 Checklist 全过。
- 迭代每轮走小闭环：需求单（变更点清单）→ 相关阶段重做 → 契约变更走硬规则 → 全量回归 → 部署。
- 每轮结束把过程文档归档（`scripts/archive_memory.py`），CHANGELOG 写清：来源、变更点、口径偏差声明、回归结果、部署记录。
- 排期吃紧时砍 🅿️1 保 MVP，核心链路不动。
