# 多 Agent 协作与防幻觉机制

> 多 agent 协作的价值不是"人多力量大"，而是**上下文隔离 + 交叉校验**。本文件定义角色、通信协议、防幻觉机制与硬规则。

## 1. 角色分工

| 角色 | 职责 | 允许读 | 禁止 |
| --- | --- | --- | --- |
| **master（编排）** | 拆任务、冻结契约、合并交付、跑脚本验收 | 目录结构、契约文档、各 agent 交付摘要 | 不读具体实现代码；不亲自编码 |
| **需求 agent** | PRD 撰写与维护 | 用户输入、PRD | 不碰代码 |
| **设计 agent** | 美术风格指导 + HTML 预览 + 品牌文案 | PRD、风格文档 | 不写业务代码 |
| **前端 agent** | 页面实现 + 消费侧契约登记 | PRD、风格指导、UI 预览、契约文档 | 不改后端；不算金额 |
| **后端 agent** | 服务实现 + 供给侧契约登记 | PRD、契约、后端需求文档 | 不改前端 |
| **数据库 agent** | DDL、索引、枚举登记 | PRD、后端文档、契约 | 不改业务代码 |
| **测试 agent** | 按文档独立验收 | PRD、契约、用例文档 | **不读实现代码** |
| **用户** | 产品决策、里程碑验收、阻塞拍板 | 交付物 | — |

> 前端/后端/数据库三个 agent 可并行施工，但契约草稿必须经 master 合并去重后**冻结**，冻结后施工。

## 2. 通信协议：只传文档路径，不传内容

- agent 之间交接只给：`文档相对路径 + 相关章节号 + 一句话摘要`。长文档绝不粘贴进对话。
- 任何 agent 引用契约字段时，**回读文档原文**，禁止凭记忆复述。这是防幻觉第一规则。
- 文档矛盾 → 停下对齐（升级 master 或用户拍板），禁止各自猜测后继续。

## 3. 上下文长度危机的缓解

1. **分层持有**：master 只持有任务清单和指针；细节文档谁负责谁读。
2. **记忆归档**：每轮迭代结束，过程文档（需求单、排查记录、审核报告）按日期归档到 `存档-YYYY-MM/`（用 `scripts/archive_memory.py`），工作目录只留当前轮次活跃文档。
3. **CHANGELOG 浓缩历史**：详细历史进 CHANGELOG，活跃上下文只放"当前版本口径"。新 agent 上线先读 CHANGELOG 最新 3 条 + 契约当前版，不读全部历史。
4. **脚本代替回顾**：重复验证用脚本（探针/lint），不用 AI 翻聊天记录回忆"上次是怎么调的"。

## 4. 互相校验（防幻觉第二规则）

| 校验对 | 机制 |
| --- | --- |
| 前端 × 后端 | 同一契约双侧实现；联调差异 = 契约歧义信号，修订契约而非私下兼容 |
| 测试 × 全部 | 测试 agent 不读实现，以文档为唯一期望源 |
| 设计 × 前端 | UI 细节审核报告逐页比对预览稿 |
| master × 全部 | 契约变更双 agent 确认后才冻结 |
| 脚本 × AI | 一切能用脚本验证的事实（字段存在、接口存活、错误码合法），以脚本输出为准，不信 AI 口述 |

## 5. 契约变更硬规则

1. 接口字段增删改 → 同步更新契约文档 + CHANGELOG，标注版本号与日期。
2. **当次交付必须重打包项目文档包**：包内契约与磁盘最新版字节一致，打包时间晚于契约最后修改时间；旧包移入存档目录，版本号连续不跳号。
3. 自标"需重打包"而未执行 = 交付未完成。
4. 用 `scripts/changelog_check.py` 自动守门：契约 mtime 晚于 CHANGELOG 最新条目即报警。

## 6. 代码协作规范（单仓 monorepo）

```
project/
├── client/（前端）  server/（后端）  migrations/（数据库脚本）
├── docs/            # 唯一事实源
├── scripts/         # 部署/种子/校验脚本
└── CHANGELOG.md
```

- 分支：`main`（只接受合并，打 tag 发布）/ `dev`（集成）/ `feature/<模块>-<简述>` / `hotfix/<简述>`。
- Commit：`type(scope): 简述`（feat/fix/docs/refactor/test/chore），正文注明关联文档章节（`PRD §5.6 / API §6.2`）。
- PR ≤ 400 行有效改动，超了先拆；必须过 lint + 单测 + ≥1 人评审；支付/退款/库存类 PR 附测试证据。
- 任何一方不得合并自己标了 breaking 的 PR 而无对方评审。

## 7. 配置漂移防护（多环境部署复读核对清单）

> 配置漂移 = 环境 E 的运行时配置 ≠ E 的配置存档。来源多为"从 dev 顺手复制改一改""只改了密钥忘了改回调地址"。防漂移靠**复读**（部署后读回运行时实际值比对），不靠"我记得我改了"。

### 7.1 部署前

- [ ] 配置只从**环境 E 自己的配置存档**取（存档 = 该环境配置的唯一事实源）；禁止从别的环境复制后"改改就用"。
- [ ] 待发布配置与存档 `diff`，只允许预期差异（如回调 URL、环境标识）；出现计划外差异 → 停下对齐，禁止带进部署。
- [ ] 密钥按 `references/backend-paradigm.md` §6 密钥红线处理：只核对存在性与指纹（如 hash 前 8 位），**禁止把密钥值打印进日志/聊天记录/部署记录**。

### 7.2 部署中

- [ ] 每次配置变更写部署记录：谁、何时、哪个环境、哪些键、旧值 → 新值（密钥只记"已轮换"不记值）。
- [ ] 变更脚本幂等可重跑（同输入重复执行结果一致），失败留日志不归零重来。

### 7.3 部署后（复读，缺一不可）

- [ ] **逐函数/逐服务读回环境变量**，与 E 的存档比对；复读的对象是运行时实际值，不是部署用的那份文件。
- [ ] 打 `buildInfo` 版本探针，复读确认线上跑的确实是目标版本（防"代码部署了但实例没换"）。
- [ ] 抽一条真实业务链路打 `scripts/probe_api.py` 探针，确认行为符合新配置（如回调地址已切到 E）。

### 7.4 发现漂移后的处置

1. 暂停该环境的新功能验证，漂移未清不算部署完成。
2. 二选一对齐，master 拍板：**以存档为准回写运行时**，或**以运行时为准回填存档**（确实有意改的）。
3. 对齐后重新走 7.3 复读；**不允许第三种状态**（存档与运行时长期不一致、各自为战）。

> 复读原则与"脚本 × AI"一致（§4）：凡能用脚本读回比对的事实，以脚本输出为准，不信"我部署时明明改了"。
