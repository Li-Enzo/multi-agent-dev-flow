# 契约版本演进指南

> 核心思想：**契约只长不老，老得有仪式**。v1→v2 只做加法；不得不破坏时，走「废弃标记 → 并行期 → 下线公告」完整生命周期，让调用方永远有退路。判定交给 `scripts/contract_diff.py`，本文档定义什么算破坏、怎么退、怎么公告。配套硬规则见 `references/agent-collab.md` §5，模板落点见 `assets/templates/api-contract-template.md` 变更管理节。

## 1. 演进总原则：v1→v2 只加不改

契约一旦发布给调用方（前端、其他 agent、外部系统），已发布部分视为**只读**。演进只允许加法：

| 方向 | 允许（向后兼容） | 禁止（破坏性） |
| --- | --- | --- |
| 接口 | 新增 action | 删除/改名 action |
| 入参 | 新增**选填**字段；必填放宽为选填 | 新增必填字段；选填改必填；删除字段 |
| 出参 | 新增字段；可选提升为必有 | 删除字段；必有降级为可选 |
| 类型 | 一律不许改（含"收窄"，如 string→int、float→int） | 任何既有字段的类型变化 |
| 错误码 | 新增码（先登记通用约定码表，`contract_lint.py` 守门） | 复用/改义既有码 |

一句话：**旧请求发过来、旧响应读出去，行为都必须不变**。

## 2. 破坏性变更判定（工具口径）

改契约前先跑 diff，别靠肉眼：

```bash
python scripts/contract_diff.py docs/api-contract.v1.md docs/api-contract.md
# 退出码 0 = 无破坏；1 = 有破坏（FAIL 明细）；2 = 文件/结构错误
```

`contract_diff.py` 判 FAIL 的五类，即本指南的破坏性变更全集：接口删除、字段删除、类型变更、新增必填入参（含选填改必填）、出参必有降级。INFO 级（新增接口/可选字段/必填放宽/可选提必有）是兼容演进，直接放行。

CI/流水线里把它挂在契约文件变更之后：FAIL 即阻断当次交付，除非这次交付本身就是一次**已公告的废弃移除**（第 4 节）。

## 3. 不得不改时：字段废弃标记

确定要退役的字段，**先标记，后移除**，两步之间隔一个并行期（第 4 节），不允许一步到位。

标记约定（落在契约表格内，人读机读两便）：

- **入参表**：字段名加删除线 `~~oldField~~`，必填列改「否」，含义列首写
  `**已废弃**：<原因>。自 vX.Y 标记，vZ 移除；迁移：改用 newField。`
- **出参表**：字段名加删除线，必有列改「否」，含义列首写
  `**已废弃**：自 vX.Y 起不再保证返回，vZ 移除；迁移：改用 newField。`
- 服务端义务：标记期间**照常返回/接受**该字段（行为不变，只是宣告），并在 CHANGELOG 记一条 `docs(contract)`。

示例（出参表片段）：

```markdown
| 字段 | 类型 | 必有 | 含义 | 示例 |
| --- | --- | --- | --- | --- |
| ~~nickname~~ | string | 否 | **已废弃**：自 v1.3 起不再保证返回，v2.0 移除；迁移：改用 profile.nick。 | 小明 |
| profile | object | 是 | 用户资料聚合对象 | {...} |
```

注意：必有降级会被 `contract_diff.py` 判 FAIL——**这一次 FAIL 是预期的**，但必须同时满足：CHANGELOG 有记录、并行期已起算。除此之外 diff 不能有第二条 FAIL（防夹带私货）。

## 4. 版本号与并行期

- **版本口径**：契约文档版本（v1.3）随模板「变更管理」节登记，与 git tag 解耦；破坏性移除允许跳大版本（v1.x → v2.0）。
- **并行期长度**：内部调用方 ≥ 2 周且覆盖一次全量回归；外部/不可控调用方 ≥ 1 个季度。并行期从**公告发出**起算，不从标记起算。
- **并行期义务**：
  1. 服务端双写/双读：新旧字段都产出，新代码只消费新字段；
  2. 监控旧字段流量（日志计数或网关报表），移除前确认旧字段调用占比已降到可接受阈值（内部归零，外部 < 1%）；
  3. 到期移除时，从契约表删行 + CHANGELOG 记 `refactor(contract)`（简述注明"移除已废弃字段"）+ 重打包文档包。
- 并行期内发现迁移受阻（调用方改不动）→ **延长并行期**，不许强推下线。

## 5. 下线公告模板

并行期起算以公告为准。公告必须可执行：谁受影响、改什么、死线、找谁。复制即用：

```markdown
# 【契约下线公告】<域>.<action> 字段 <oldField>

- **影响范围**：调用 <action> 的 <前端/服务/外部合作方>。
- **变更内容**：出参/入参字段 `oldField` 将于 <YYYY-MM-DD>（<版本>）移除，
  请迁移至 `newField`（语义差异：<一句话>）。
- **时间线**：vX.Y（<日期>）标记废弃 → 并行期至 <日期> → vZ（<日期>）正式移除。
- **迁移指引**：<改前/改后请求与响应示例各一段>。
- **联系人**：<owner>；迁移受阻请在 <日期> 前提出，将评估延长并行期。
```

内部项目可贴在 CHANGELOG 顶部 + 项目群；外部调用方走正式渠道（邮件/开放平台公告），模板不变。

## 6. 工具链守门（串成一条线）

| 时点 | 工具 | 作用 |
| --- | --- | --- |
| 写契约时 | `contract_lint.py` | 结构完整性 + 错误码登记合法性 |
| 交付前 | `contract_diff.py` | 对比上一版，破坏性变更 FAIL 阻断 |
| 交付时 | `changelog_check.py` | 契约 mtime 晚于 CHANGELOG 最后一条即报警 |
| 打包时 | `doc_pack.py --verify` | 文档包 manifest 完整性自检 |

演进纪律的执行不靠自觉：diff FAIL 必须为零（或仅剩已公告的那一条废弃降级），四道工具全绿才算一次合规的契约交付。
